C-1 — Enter gate whitelist bypass

Anyone can bypass an IKR enter gate's whitelist by deploying an adapter from the registered factory and self-admitting

Severity

Low

Justification: the gate's credit-side whitelist is bypassable by any account, deterministically, with no privileged role and no share requirement. No funds are lost and no exit is blocked. Medium is arguable only where the gate is the compliance boundary of a permissioned pool rather than a soft preference.

Context

- src/adapters/midnight/gates/IKRCompatibleEnterGate.sol:36-45 (scoped contract, admit)

- src/adapters/midnight/gates/interfaces/IIKRCompatibleEnterGate.sol:9-16

- src/adapters/midnight/MidnightAdapter.sol:457-464 (adapter admits the taker in forceDeallocate)

- src/adapters/midnight/MidnightAdapter.sol:564-572 (adapter only validates the gate factory on a first buy)

- src/adapters/midnight/MidnightAdapterFactory.sol:26-37 (permissionless adapter creation)

- lib/midnight/src/Midnight.sol:384-387 (Midnight calls canIncreaseCredit(buyer) on every credit-increasing buy)

Description

IKRCompatibleEnterGate.admit authenticates only the factory that deployed the caller. It never checks the caller itself, the vault, or the admitted user's share balance:

function admit(address user, address adapterFactory) external {
    require(admitEnabled, AdmitDisabled());
    require(
        admitterFactory[adapterFactory] && IMidnightAdapterFactory(adapterFactory).isCreated(msg.sender),
        Unauthorized()
    );
    admitted = user;
    emit Admit(msg.sender, user, adapterFactory);
}

MidnightAdapterFactory.createMidnightAdapter is permissionless, and MidnightAdapter's constructor only calls asset() and setIsAuthorized() on its arguments. Nothing requires parentVault to be a real vault, and nothing requires the caller to be debt-free.

So any account can:

1. deploy a stub contract exposing asset();

2. deploy an adapter from the registered MidnightAdapterFactory with that stub as parentVault;

3. call admit(attacker, factory) from that adapter;

4. buy the gated offer directly on Midnight as an ordinary taker — the fake adapter is never touched again.

The gate's own NatSpec says the caller "must be debt-free, check the buyer holds its vault's shares". Neither property is verified on-chain, and the caller need not be a vault adapter at all.

Impact

The credit-side whitelist of an IKR enter gate is the documented gatekeeper for who may take credit in gated markets. With admission enabled (the standard configuration for gated markets), that whitelist is advisory: any address can enter any market using that gate, at any time, without permission, without holding a single vault share, and without interacting with the whitelister.

Consequences:

- A permissioned/KYC pool loses its entry restriction; non-whitelisted accounts can take maker offers and hold credit.

- Whitelisted buyers compete with an unbounded set of entrants for the same liquidity.

- The bypass is repeatable and requires no setup capital beyond the offer price.

Not affected: pricing, exits, existing positions.

Likelihood

High. No privileged role, no capital lock-up, no timing constraint. The attack is a single transaction buildable by any EOA after one adapter deployment, and it is repeatable against every offer in every market using that gate for as long as admitEnabled is true.

Recommendation

Bind the admission to something the gate can verify itself:

1. Bind to the vault. Require IMidnightAdapter(msg.sender).parentVault() to be a vault already known to the gate, and require parentVault.balanceOf(user) > 0 at admission time — two staticcalls to contracts the gate already trusts.

2. Bind to registered pairs. Have the roleSetter register (vault, adapter factory) pairs instead of bare factories, and admit only registered pairs, in addition to the existing isCreated check.

Either closes the stub-adapter path. Option 1 also restores the documented "debt-free + holds shares" semantics instead of trusting the caller.

Known issues

- Cantina draft (2026-10-12-midnight-adapter-cantina-draft.pdf): no finding mentions admit, admission or whitelist (the two admit matches are prose about caps and offer authorisation).

- TrustSec draft (2026-10-12-midnight-adapter-trustsec-draft.pdf): zero matches for admit/admission/whitelist.

- Neither TRST-CR-1..4 role description covers it: they describe the curator's trust over the gate's controller, not the gate's own authentication.

Notes

- The attacker still pays the offer price; the bypass concerns *who may enter*, not free liquidity.

- The admitted slot is transient and is cleared by a genuine adapter in the buyer callback; the fake adapter simply never clears it, which is harmless because transient storage resets at the end of the transaction.

C-2 — skim sweeps loan asset

skim treats the adapter's own loan token as stray dust and sweeps it without adjusting accounting

Severity

Info

Justification: no accounting variable is mutated by the sweep (netCredit is untouched), so a position cannot be corrupted by it. The loss is limited to whatever loan token happens to sit in the adapter outside of a deallocate withdrawal at the moment the recipient calls skim.

Context

- src/adapters/midnight/MidnightAdapter.sol:395-400 — skim(address token)

- src/adapters/midnight/MidnightAdapter.sol — realAssets() values positions from netCredit, never from loanToken.balanceOf(address(this))

- src/adapters/midnight/MidnightAdapter.sol — deallocate withdraw branch sequence: withdrawToVault(market, assets) then parentVault.deallocate(...) pulls exactly assets

Description

skim is the "sweep stray tokens" escape hatch:

function skim(address token) external {
    require(msg.sender == skimRecipient, NotAuthorized());
    uint256 balance = IERC20(token).balanceOf(address(this));
    SafeERC20Lib.safeTransfer(token, skimRecipient, balance);
    emit Skim(token, balance);
}

There is no exclusion for asset. Combined with the fact that realAssets() is derived from netCredit (never from the adapter's token balance), the adapter's entire loan-token balance is considered unaccounted and sweepable at all times.

Normally the balance is 0 between transactions because:

- buys pull exactly buyerAssets from msg.sender via withdrawToVault, and Midnight forwards the same amount out;

- withdraws pull exactly the requested assets into the adapter and the vault then pulls the same amount back.

So the sweep is only reachable against residual balance: dust left by a partial path, a direct donation, or any future code path that leaves asset sitting in the adapter for a transaction boundary. The interesting property is not that the transfer happens (it is the intended behaviour of a sweep function), but that it happens silently against the accounting asset, with no reconciliation: after a skim of, say, 5e18 loan token, netCredit is unchanged and realAssets() reports the same total as before.

Impact

- Loan token held by the adapter outside netCredit is removable by skimRecipient with no trace in accounting.

- skimRecipient is a curator-controlled, timelocked parameter. On a vault where it is set to the curator, dust from the accounting asset is effectively curator income.

- No position, no exit and no share price can be broken by the sweep itself, since nothing is recomputed from the balance.

Likelihood

N/A (behavioural, not an attack): requires only that the adapter hold asset and that skimRecipient calls.

Recommendation

Either of:

1. keep skim as-is and document that asset is sweepable too (accounting never reads the balance, so the behaviour is consistent — this is arguably correct and needs no code change), or

2. add if (token == asset) require(loanToken.balanceOf(address(this)) >= pendingWithdraw)-style guard if a future path is expected to hold asset across transactions.

Known issues

The only repo tests calling skim are test/MidnightAdapterTest.sol:5233 and :5245, both with rewardToken; none uses loanToken.

This one is largely known. TrustSec TRST-CR-4 ("Skim recipient") states that the skim recipient "can withdraw any funds that are owned by the adapter. This includes rewards ... User funds are not accessible since they are owned by the vault." So the capability is acknowledged as a centralization risk. What TRST-CR-4 does not state, and no test demonstrates, is the part this PoC targets: asset itself is swept, accounting is not reconciled, and a live position is unaffected while the balance goes to zero — the reviewer must reason from realAssets() to see that a swept asset balance is invisible to the share price.

Cantina draft: zero occurrences of skim.

Notes

skimRecipient must be the caller — calling from any other address reverts NotAuthorized(), which is why the PoC pranks the recipient.
